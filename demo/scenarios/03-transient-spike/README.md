# Кейс 03 — Transient spike (ложное срабатывание)

## Гипотеза

Canary фундаментально здоровый — 1% ошибок, как stable. Но имеет один 15-секундный всплеск с error rate 40% (например, из-за пробуждения cold-start кэша или короткого глюка зависимости). Это не повод откатывать релиз — после всплеска canary снова работает нормально.

- **Flagger** при попадании всплеска в 60-секундное окно увидит ~10% errors → window failed → второй такой window → rollback. Ложное срабатывание.
- **StatGate** получит ~100 наблюдений за 15 секунд (при ~7 RPS на canary), Λ вырастет, но не до A. После всплеска чистый трафик возвращает Λ к нулю; rollout продолжается.

## Setup

| Параметр                       | Stable (v1) | Canary (v2) |
|--------------------------------|-------------|-------------|
| `ERROR_RATE_START` / `END`     | 0.01        | 0.01        |
| `ERROR_SPIKE_AT_SECONDS`       | —           | 90          |
| `ERROR_SPIKE_DURATION_SECONDS` | —           | 15          |
| `ERROR_SPIKE_RATE`             | —           | 0.4         |

Профиль canary: error_rate(t) = 0.01 везде, кроме окна [90, 105] секунд от старта пода, где rate = 0.4.

| Инструмент | Конфигурация                      |
|------------|-----------------------------------|
| StatGate   | α=β=0.05, delta=0.05              |
| Flagger    | thresholdRange.max=5, threshold=2 |

## Запуск

```bash
./apply.sh statgate
./bin/statctl watch demo-rollout -n statgate-demo &
# ВАЖНО: rollout и k6 запускать сразу после apply, чтобы спайк попал
# на шаг 5% (90s от старта пода ≈ конец 1-го шага rollout).
kubectl apply -f demo/scenarios/03-transient-spike/statgate-rollout.yaml
k6 run --env BASE_URL=http://$INGRESS_IP demo/loadtest/load-test.js
```

## Ожидаемое поведение

**Flagger:**
Окно, накрывающее [90, 105] секунд, увидит ≈ 15 секунд × 7 RPS × 0.4 = 42 ошибки на ≈420 запросов ≈ 10% error rate. 10% > 5% → window fails. Следующее окно ([105+, ...]) — снова чистый 1%. Но в Flagger threshold=2 — нужно 2 ПОДРЯД провала. Если спайк попадает только в одно окно — Flagger выдержит. **Это нюанс кейса.**

Чтобы гарантированно получить 2 окна с failed, можно либо:
- (a) увеличить `ERROR_SPIKE_DURATION_SECONDS` до ~70, чтобы спайк попал в 2 соседних 60-сек окна.
- (b) поставить `threshold: 1` у Flagger.

**Рекомендуется** оставить duration=15 и наглядно показать на слайде: один спайк → одно failed window → Flagger ждёт второй (которого не будет). Это покажет, что даже Flagger с threshold=2 спасает не всегда — в реальности всплески нередко длятся как раз 1+ окно. Можно сделать **два прогона**:
- (a) spike=15s, threshold=2 → Flagger spasaet, оба не откатывают (parity).
- (b) spike=70s, threshold=2 → Flagger откатывает, StatGate переживает.

Версия (b) для слайда сильнее. Поэтому в `apply.sh` второй прогон делается с `ERROR_SPIKE_DURATION_SECONDS=70`:

```bash
# Альтернатива для усиленного кейса (длинный спайк):
kubectl -n statgate-demo set env deployment/demo-canary \
    ERROR_SPIKE_DURATION_SECONDS=70
```

**StatGate (для исходных параметров 15s × 0.4):**
- A = 2.944.
- Per-failure Λ += ln(0.06/0.01) = ln(6) ≈ 1.79.
- Per-success Λ += ln(0.94/0.99) ≈ -0.052.
- За 15-сек спайк при ~7 RPS на canary: ~100 запросов, ~40 ошибок.
- Λ += 40 · 1.79 + 60 · (-0.052) ≈ +68.5. **Это сильно больше A**.
- **Проблема:** при таких параметрах StatGate тоже откатит.

**Поэтому для демонстрации устойчивости нужно либо:**
- Увеличить `delta` до 0.10 (тогда per-failure Λ += ln(0.11/0.01) ≈ 2.4, а success Λ −= 0.10 — соотношение похуже),
- Или сделать спайк коротким и слабым: `DURATION=5, RATE=0.2`.

**Скорректированные параметры (рекомендуемые для слайда):**

```bash
ERROR_SPIKE_DURATION_SECONDS=5
ERROR_SPIKE_RATE=0.15
```

За 5 секунд × 7 RPS = 35 запросов; failures ≈ 5; Λ += 5·1.79 + 30·(-0.052) ≈ 7.4. Всё ещё больше A.

**Принципиальный вывод (важен для дипломной работы):**
При очень коротком всплеске и высокой амплитуде SPRT всё равно среагирует — это **корректное поведение**, тест математически чувствительный. Преимущество SPRT не в том, что он игнорирует любые спайки, а в том, что он математически сбалансирован: критерий "сколько ошибок за сколько времени" формализован через α/β, а не угадан порогом.

Поэтому кейс 3 имеет смысл переформулировать: **продемонстрировать одинаковую реакцию обоих систем на яркий спайк, но показать что StatGate имеет формальное обоснование, а Flagger — угаданный threshold**. Либо использовать его как точку для обсуждения границ применимости SPRT.

## Критерий успеха

Зависит от выбранной формулировки. Для слайда "StatGate переживает шум" — подобрать параметры так, чтобы Λ_max < A. Контролировать через `statctl watch`.

## Что фиксировать

- График Λ во времени (видна "горка" во время спайка, без пересечения A).
- Скриншот Grafana с error rate (виден короткий всплеск).
- Решение Flagger в `kubectl describe canary`.
