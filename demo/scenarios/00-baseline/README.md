# Кейс 00 — Baseline (happy path)

**Стартовый кейс презентации.** Показывает, что в нормальной ситуации система работает как ожидалось: чистый канареечный rollout проходит все шаги и promote'нется до 100%.

## Гипотеза

Canary не отличается от stable по error rate — обе версии работают с 0% ошибок (новая версия по факту лучше или эквивалентна старой). В этой ситуации:
- **StatGate** должен накапливать Λ в сторону B (нижняя граница) на каждом шаге и promote rollout.
- **Flagger** должен видеть error rate 0% < 5% во всех окнах и тоже promote.

Это **обязательная проверка**, что оба инструмента не ложно-положительны (не блокируют здоровые релизы).

## Setup

| Параметр                              | Stable (v1) | Canary (v2) |
|---------------------------------------|-------------|-------------|
| `ERROR_RATE_START` / `ERROR_RATE_END` | 0           | 0           |
| Описание                              | без ошибок  | без ошибок  |

| Инструмент | Конфигурация решения                                 |
|------------|------------------------------------------------------|
| StatGate   | α=β=0.05, delta=0.05 (стандартный МДЭ)               |
| Flagger    | thresholdRange.max=5, threshold=2 (2 подряд провала) |

## Запуск

```bash
# Прогон 1: StatGate
./apply.sh statgate
./bin/statctl watch demo-rollout -n statgate-demo &
k6 run --env BASE_URL=http://$INGRESS_IP demo/loadtest/load-test.js

# Сброс
./apply.sh reset

# Прогон 2: Flagger
./apply.sh flagger
kubectl describe canary demo -n statgate-demo
k6 run --env BASE_URL=http://$INGRESS_IP demo/loadtest/load-test.js
```

## Ожидаемое поведение

**StatGate:**
- Λ должна стабильно уменьшаться (success-инкременты отрицательные, failure'ов почти нет).
- При delta=0.05, p₀≈0, p₁=0.05: per-success Λ += ln((1-0.05)/(1-0)) ≈ -0.0513.
- На каждом шаге за ~60 секунд накапливается ~60 успехов на canary при низком весе и больше при высоком → Λ уходит ниже B = -2.944.
- После promote-decision на каждом шаге переходим к следующему. Финальная фаза: **Promoted**.
- Общее время: ~3 минуты (4 шага × 60 секунд, минус последний с pauseSeconds=0).

**Flagger:**
- Каждые 60 секунд error rate query даёт 0% (или ~NaN из-за деления 0/0, что Flagger трактует как «нет ошибок»).
- 0% < 5% во всех окнах → все iterations pass.
- Шаги 20 → 40 → 60 → maxWeight 50 → Promotion completed.
- Финал: **Succeeded**.

## Критерий успеха

Оба инструмента: **promote завершён без ошибок**.

| | StatGate | Flagger |
|---|---|---|
| Финальное состояние | Promoted | Succeeded |
| Откатов | 0 | 0 |

Если хоть один откатил здоровый canary — это false-positive, говорит о неправильно подобранных параметрах (например, слишком маленькая delta при шумном baseline).

## Что фиксировать

- Финальная фаза для обоих прогонов.
- Скриншот Grafana: панель **SPRT Λ** (видно, как кривая уходит вниз и пересекает B на каждом шаге).
- Скриншот Grafana: панель **Rollout Phase** — переход Pending → Running → Promoted.
- Скриншот Grafana: панель **Canary Traffic Weight** — ступенчатый рост 5 → 25 → 50 → 100.

## Зачем этот кейс в презентации

1. **Доказательство правильности.** Без него комиссия может спросить «а как доказано, что вы не блокируете нормальные релизы?». Этот кейс — формальный ответ.
2. **Контраст для последующих сценариев.** Зритель видит «вот как должен выглядеть успешный rollout» — потом сразу понимает, что во 02-slow-drift Λ ведёт себя иначе.
3. **Демонстрация α-гарантии в действии.** Здоровый canary не откатывается — α (вероятность ложного отката) держится в заявленных 5%.
